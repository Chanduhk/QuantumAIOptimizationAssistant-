# F9.1D Legacy Model and Optimization Readiness

**Decision: `F9.1D = INSUFFICIENT_EVIDENCE`**
**Scope:** forensic/readiness audit only. No source, model, database, API, or frontend changes were made.

## 1. Executive summary

The repository has additive F9.1C duration and prediction-provenance contracts. They reject optimizer inputs without an explicit duration unit and mark the legacy trained prediction as `MODEL_FEATURE_UNIT_UNVERIFIED`. Those safeguards are useful, but they do not resolve the semantics of existing task rows or prove what duration unit a serialized legacy model learned.

No ProductivityModel artifact was found in the repository tree or its expected application artifact directory at audit time. The active model serializer stores the estimator, task-type encoder, feature names, and training data shape, but not semantic unit/schema provenance, target definition, dataset identity, validation metrics, or model version. The training target is generated by heuristic formulas over task priority, duration ratio, hour, and an energy curve. This is not an observed productivity outcome. F9.1E adds those metadata fields for newly trained versioned artifacts; old artifacts remain unverified.

The current code can produce individual task/hour predictions under the F9.1C provenance method, but trained outputs remain optimizer-ineligible and cold-start outputs are hour-only heuristics. No production task-by-hour matrix, valid real-data non-triviality result, or compatible model artifact is available. The synopsis’s broader classical → suitability → QUBO → Ising → local QAOA simulation → hybrid comparison → Executive Cognitive Brain workflow remains the intended architecture; existing generic quantum modules do not establish that this production scheduling problem is ready for them.

## 6. Historical duration semantics

`Task.estimated_duration` remains a public/database float with no universal unit. Current UI minutes are a path-specific observation, not historical truth. The F.3 ORM adapter labels the mapped estimate as minutes, while schedulers generally consume raw values as hour-like quantities. These are conflicting assumptions, not a safe conversion rule. **No historical unit can be inferred from magnitude, filename, current UI, or scheduler arithmetic.** Historical optimizer eligibility remains false unless a trusted per-record source establishes the unit.

## 8. Dataset audit

The legacy behavior training path collects completed tasks with start/end times. It builds `duration` by preferring stored `actual_duration`, then estimate; it computes a clipped actual/estimated ratio and uses that, priority, and fixed hour-based curves to derive `focus_score`, `energy_level`, and `productivity_score`. The model target is therefore **heuristic-derived**, not ground truth. Legacy estimates may be untyped, and the stored behavior row retains no duration unit/provenance.

The separate F.3 event dataset has explicit minute-named duration fields and computes a duration-ratio target from actual outcome data. Its feature builder records estimate-at-prediction and excludes actual duration from forward features. It is safer for leakage boundaries, but its target is completion-duration ratio rather than measured productivity, and there is no evidence this dataset currently trains the legacy ProductivityModel.

Tests and quick-start/demo generators contain synthetic values. They are test mechanics/examples only and do not establish production-data history, model quality, or task/hour interaction.

## 10. Prediction path audit

`PredictionEngine.predict_task_hour_with_provenance` is additive and leaves existing public scalar methods intact. It requires an optimizer-eligible `DurationValue`, candidate hour 6–22, task identity/type, and reports productivity points, status/source, model state, duration provenance, history-count availability, `model_version=None` with `MODEL_VERSION_NOT_AVAILABLE`, fallback, validity, and eligibility.

- **Cold start:** `COLD_START_HEURISTIC`, `fallback_used=true`, `model_trained=false`; the existing formula varies only by hour and is not personalized or task-hour evidence. For a truly empty in-memory history frame, count may be 0; otherwise missing count remains unavailable.
- **Trained legacy model:** returned score is marked `MODEL_FEATURE_UNIT_UNVERIFIED`. History count and model version were unavailable from legacy artifacts lacking semantic metadata. Newly trained compatible artifacts expose their recorded sample count and version; legacy artifacts remain unavailable/ineligible.
- **Unavailable/invalid:** represented distinctly by the structured result.
- **Production eligibility:** no current result status makes the unverified legacy model optimizer-compatible; cold-start is also ineligible.

## 11. Leakage audit

- **F.3 dataset path:** actual completion duration is used as a label/outcome and excluded from forward prediction features, by design.
- **Legacy behavior/model path:** actual duration is used in constructed training `duration` features, and actual duration may be a fallback input in legacy prediction/scheduling helpers when estimate is absent. That is a **LEAKAGE_RISK / train-inference semantic mismatch** for forward task planning. F9.1C adapter prevents using actual duration as an estimate, but does not retrofit the older public prediction path.
- Completion timestamps are used to derive observed duration in historical training/dataset construction; those are outcome facts, not valid at prediction time.
- No code was changed to “fix” this because doing so safely requires a versioned dataset/feature contract and compatibility plan.

## 18. Optimization readiness gate

**Final decision: `F9.1D = INSUFFICIENT_EVIDENCE`.** The repository cannot prove historical units, legacy model feature-unit semantics, deployed artifact identity/provenance, or genuine production task/hour interactions. This fits the prompt’s definition of insufficient evidence; it is not a claim that QUBO/QAOA algorithms are technically impossible. F9.2/classical optimization should not consume this prediction path yet.

## 19. Required changes before readiness

1. Define an additive, explicit unit/source contract for new task estimates while leaving legacy `estimated_duration` untouched; do not infer units for existing rows.
2. Resolve trustworthy per-record provenance for any legacy rows proposed for use, or exclude them.
3. Define a versioned ML feature schema with identical, explicit normalization at training and inference; separate actual outcome from prediction-time features.
4. Define an outcome-backed target suitable for the intended objective, or clearly bound the use of heuristic targets; establish data lineage, preprocessing, feature order, model version, dataset/version, sample count, and validation protocol in the artifact.
5. Train/validate a new artifact only after the above semantics are approved and real eligible data exist; do not relabel/retrain from guessed historical values.
6. Only then evaluate real task-hour cells and the non-triviality condition; build the common optimization problem/evaluator after those gates pass.

No database migration is required to record this finding. Whether a later additive metadata migration is needed depends on the approved persistence/API contract. Do not mass-convert legacy values.
