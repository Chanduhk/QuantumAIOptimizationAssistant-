# F9.1A — Classical Optimization Foundation: Source-Grounded Design

**Design status: PARTIAL (minimum formulation identified; production proof/approval gates remain).**

**Scope:** design only. No production source, tests, simulator, API, or frontend were changed. No QUBO, Ising, or QAOA was implemented or executed.

## 1. Authority and current status

The Synopsis is the intended architecture: input → memory/knowledge → behavior and ML → prediction/planning/decision/intelligence → classical optimization → quantum suitability → QUBO → Ising → QAOA → candidate comparison → Executive Cognitive Brain → recommendation → execution/outcome/feedback/learning.

The Synopsis is not evidence that each stage is connected or trained in this repository. The code is authoritative for current implementation. The Synopsis gives no numerical scheduling objective weights. The prior F9.0/F9.1 findings remain accurate for the **current canonical optimizer**: its task/hour assignment score is invariant under task permutation across a fixed hour set, and the RL reward is separable into task-only and hour-only terms.

## 3. Minimum defensible problem (conditional design)

The smallest source-aligned assignment problem is to **assign task identities to the distinct start hours already proposed by the existing RL scheduler**, optimizing the existing behavior predictor's productivity score for each task/hour pair. This does not ask a second scheduler to invent hours or replace the RL hour-selection behavior. It formalizes the currently missing task-to-hour matching step.

This is a constrained **single-objective** foundation, not a claim that the repository already supports multi-objective schedule optimization. The existing DecisionEngine weighted score and MultiObjectiveOptimizationEngine weighted scenario ranking retain their existing semantics; neither becomes a schedule objective here.

### Data and applicability gate

For each actual task `t` and each proposed hour `h`, build:

`p[t,h] = PredictionEngine-normalized(BehaviorIntelligenceEngine.predict_task_productivity(hour_of_day=h, task_type=t.task_type, duration=normalize_duration(t.duration, approved_model_unit)))`

The matrix is eligible only when:

1. The behavior predictor is genuinely trained from the user's existing task history (not the cold-start profile).
2. Model training state, history count, and prediction source are carried with the problem.
3. Inputs and all scores are finite and score values satisfy the existing 0–100 contract.
4. The instance's feasible assignment objective is non-constant. If not, it must be reported as degenerate and must not be described as a meaningful optimization case.

The current model has a minimum training size of three rows, but that is only an implementation validation threshold, not a statistical sufficiency/quality guarantee. The target `productivity_score` is generated by `BehaviorIntelligenceEngine.extract_features` from priority, completion-duration ratio, time focus, and a deterministic energy curve. In addition, lifecycle derives `actual_duration` in minutes (`ACTUAL_DURATION_TOLERANCE_MINUTES`), while scheduling treats the raw duration as hours; ProductivityModel training documentation labels duration as minutes but prediction documentation labels it as hours. A consistent duration-unit contract and normalization is a prerequisite before this predictor objective can be used. Therefore the objective must be named **predicted heuristic productivity score**, not measured productivity or validated user outcome. At cold start the predictor returns an hour-only fallback; that path fails the assignment-interaction condition and is ineligible for the optimization objective.

### Decision variables

For fixed tasks `T` and the distinct RL-proposed hour set `H`:

`x[t,h] ∈ {0,1}`, where 1 means task `t` is assigned to start at hour `h`.

Use only instances where `|T|=|H|`, `2≤|T|≤17`, and every RL result contains a distinct integer hour in 6–22. The 2-task minimum is necessary for an assignment permutation to exist. The 17-task bound follows the RL action set; duplicate fallback hours invalidate the formal input.

### Hard constraints

| Constraint | Mathematical form | Existing source / status | Test method for later implementation |
|---|---|---|---|
| Each task once | `Σ(h∈H) x[t,h] = 1` for all `t` | RL emits one assignment per input task; formal candidate validator is missing | Reject missing/duplicate task IDs; count assignments per task |
| Each proposed start hour once | `Σ(t∈T) x[t,h] = 1` for all `h` (given equal cardinality; the underlying rule is at-most-one) | `RLScheduler.used_hours` / `_pick_available_hour` avoids repeated starts while slots remain | Reject duplicate hours; exhaustive candidate checks for small instances |
| Only proposed hours | `x[t,h]` exists only for `h∈H`; `H⊆{6,…,22}` | RL action domain and actual RL output | Reject out-of-domain or unproposed hours |

Duration remains a validated numeric task attribute and predictor input, but is **not** converted to occupancy. Existing canonical code does not prevent intervals from overlapping. This minimal problem therefore formalizes the existing distinct-start-hour assignment only; it must not be advertised as a capacity-feasible or non-overlapping calendar. If HELIOX requires those properties, a separately approved resource/interval semantics must be added before that broader claim.

No deadline or dependency constraint is included: the persisted task model has no deadline, and dependency analysis does not enforce chronological placement in the canonical daily scheduler.

## 4. Objective, comparison, and non-triviality

Objective:

`maximize F(x) = Σ(t∈T) Σ(h∈H) p[t,h] · x[t,h]`

This sums the existing predictor score for every assigned task. There are no new objective weights or unsupported terms. Since the task set is fixed, sum and mean rank candidates identically; the sum matches the project's existing aggregate-score pattern. Task priority is not added as another term: all tasks are required, so a task-only priority sum cannot change the assignment choice.

An assignment permutation is non-trivial only if the actual matrix allows it. For two tasks A/B and slots h1/h2, the swap difference is:

`Δ = p[A,h1] + p[B,h2] − p[A,h2] − p[B,h1]`.

Require at least one pair of feasible assignments with different evaluator-computed objective values before reporting a non-trivial instance. No illustrative score values are asserted as real user/model output here. A future deterministic unit fixture may exercise the algebra, but production evidence must come from the user's actual trained model and must retain provenance.

### Multi-objective alternatives

- Weighted sum: **not supported for scheduling**. Existing weights apply to task ranking or simulated-future ranking, not schedule candidates.
- Lexicographic: no existing schedule objective order defines it.
- Normalized objective vector: no validated set of assignment-varying dimensions/scales.
- Pareto: no schedule Pareto-frontier implementation; the future engine performs weighted ranking, not Pareto analysis.
- User-defined weights: no current task-schedule preference contract.

Therefore use a single source-defined predictor score as the minimum foundation, with feasibility as hard constraints. Do not claim this completes the Synopsis's broader multi-objective decision-making capability.

## 5. Shared problem and evaluator design

Later implementation should use one immutable problem containing:

- stable problem ID;
- task IDs plus task type, validated duration and other predictor inputs;
- the exact RL-proposed slot set;
- deterministic task-major/hour-ascending score matrix;
- objective ID/formula and source;
- predictor training state, history/sample count, and prediction provenance;
- supported hard constraints and their scope/version.

A candidate contains assignments and solver/runtime identity only. A common evaluator must independently validate all constraints and recompute `F(x)` from the problem's stored score matrix; solvers may not submit authoritative scores. A comparison stores both evaluated candidates, feasibility/objective evidence, and a deterministic selection reason. For ties, use stable assignment ordering; do not prefer a solver by identity.

The current `ExecutiveCognitiveBrain.execute_planning_request(..., quantum_result=...)` can later receive hybrid evidence, but it is downstream and must remain the final recommendation layer. No parallel Brain or planning route is required.

## 6. Classical reference solver

Minimum solver: deterministic maximum-weight bipartite assignment over `T×H`, using the exact stored `p[t,h]` matrix and the same one-to-one constraints. A standard-library bitmask dynamic program is sufficient for the bounded 17-slot domain (`O(|T|·2^|H|·|H|)`); use a stable task/hour order and deterministic tie-breaking. It needs no new dependency.

The existing RL scheduler remains the source of proposed slots and can also supply an incumbent assignment. Do not remove it. In a later source change, integrate the reference assignment at the existing `OptimizationEngine` stage and compare it using the common evaluator; preserve current external behavior until candidate evidence and compatibility tests justify activation. Do not create a new REST route or bypass `AIBrainController`/`DecisionPipeline`.

## 7. QUBO readiness (assessment only)

**QUBO CONDITIONALLY READY** for the bounded matching problem, only if the model gate and non-constant objective check pass:

- binary variables: `|T|·|H|`;
- objective: linear coefficients from `p[t,h]` (negated for minimization if required by the formulator);
- exact-one constraints: quadratic penalty `(1−Σ_h x[t,h])²`;
- at-most-one/hour constraints: pairwise quadratic collision penalties;
- finite deterministic coefficients: validate predictor scores and deterministic variable order.

A future penalty bound can be derived from the actual matrix, not guessed. Because each score is in `[0,100]`, an upper bound on the absolute objective coefficient sum is `Σ|p[t,h]|≤100|T||H|`; select penalties from a proof against that instance bound, not a fixed unexplained constant. This document does not instantiate coefficients or create a QUBO. Duration-unit normalization is unresolved, so the score matrix itself is not currently ready to build.

Current E.7/QAOA configuration permits at most 8 variables by default. Here the variable count is `n²` because `|T|=|H|=n`; `n=2` gives 4 variables and `n=3` gives 9, which exceeds the current default. Suitability must apply configured simulator limits after formulation and must route larger problems to a classical candidate. No quantum advantage follows from feasibility or execution.

Duration-aware non-overlap, deadlines, task dependencies, resource capacity, risk, and multi-day constraints are outside this QUBO contract until the corresponding semantics exist.

## 8. Ordered implementation plan (future approved phase)

1. **Provenance:** expose predictor `is_trained`, training sample/history count, source (`trained_heuristic_labels` or `cold_start_heuristic`), and score bounds in the immutable optimization problem. Never manufacture history; reject/route classical-only when untrained.
2. **Problem builder:** after existing RL slot proposal, create deterministic task-hour predictions for those exact slots; reject invalid/duplicate slots and degenerate objective matrices.
3. **Common evaluator:** implement assignment, slot-domain, objective, and violation checks independently of solver output.
4. **Classical reference:** solve maximum-weight matching deterministically and evaluate it through the common evaluator. Retain the RL assignment as an additional evaluated incumbent.
5. **Compatibility:** integrate at the existing OptimizationEngine stage without removing RL; test compatibility before changing which candidate becomes the active schedule.
6. **Executive comparison:** deliver only evaluated candidate evidence to the existing executive layer; maintain classical fallback.
7. **Quantum later:** only after the classical contract is accepted, adapt this same problem to QUBO, apply configured suitability, then use existing Ising/QAOA/hybrid modules. F9.1A does none of this.
8. **Scope expansion separately:** define and test interval capacity, deadline persistence, and dependency precedence only if product requirements approve them.

## 10. Explicitly unsupported or still unproven

- Non-overlapping task intervals and duration-based capacity.
- Persisted deadline windows or deadline feasibility.
- Chronological dependency constraints in the daily scheduler.
- A validated multi-objective schedule comparison policy.
- Per-prediction uncertainty or calibrated confidence.
- A non-separable score matrix from any particular user's actual trained model; it must be measured per problem instance.
- User outcome validation for the heuristic productivity label.
- Any physical quantum execution or quantum advantage.

**Decision:** the minimum mathematical model can be specified conditionally from the existing predictor and RL-proposed slots, without new weights. The current canonical system does not materialize or provenance-tag the task-hour matrix, no actual trained-user matrix was inspected or proven non-separable, and duration units are inconsistent across lifecycle, scheduling, training, and inference. Therefore the design is **PARTIAL**, not production-ready; resolve these gaps and accept the non-triviality gate before implementation.
