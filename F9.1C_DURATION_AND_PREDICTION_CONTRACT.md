# F9.1C — Duration Semantics and Prediction Provenance

**Status: IMPLEMENTED WITH KNOWN LIMITATIONS.** This phase adds an internal, explicit duration contract and a structured task/hour prediction result. It does not normalize persisted historical values, alter Task API fields, change scheduling semantics, or make a legacy ProductivityModel safe for optimization.

## 1. Duration policy

- **Current lifecycle writes:** `TaskLifecycleService.complete_task` calculates `(completed_at - start_time).total_seconds() / 60.0`; `Task.actual_duration` therefore means minutes for values written by that path. Its public/database field remains unchanged.
- **Existing `Task.estimated_duration`:** its unit is unknown for untagged legacy values. No row is rewritten or presumed to be hours/minutes.
- **Current UI path:** the task creation form labels and validates the estimate in minutes and sends the existing `estimated_duration` field unchanged. This does not establish a global unit for every public/ORM writer.
- **Optimizer internal unit:** hours. New internal inputs must state unit and source. Supported units are `minutes` and `hours`; unknown units are rejected for optimizer eligibility.

`backend/app/domain/optimization_input_contract.py` adds:

- `DurationUnit`, including `UNKNOWN` for classification (never accepted by normalization);
- `LegacyUntypedDuration` and `classify_legacy_duration`, which retain a raw value and mark it optimizer-ineligible;
- immutable `DurationValue`, retaining original value/unit/source, normalized hours, conversion record, and known-unit status;
- pure `normalize_duration(value, unit, source)`; it rejects booleans, nonnumeric, non-finite, non-positive, unknown unit, and missing provenance; minutes convert by `/60`, hours use identity;
- `OptimizationTaskInput` and `adapt_task_for_optimization`, which require an explicit estimate unit/source and never substitute `actual_duration`.

No global maximum task duration is enforced: repository consumers disagree and no universal limit exists. An upper bound must be approved before introducing one.

## 2. Optimizer task eligibility

The adapter accepts only a stable positive integer or non-empty string task ID, task type, priority 1–5, explicit lifecycle/completed state, optional boolean `outcome_valid`, and a valid explicit estimate. It rejects:

- an untagged estimate with `LEGACY_UNTYPED_DURATION`;
- missing estimate with `MISSING_ESTIMATE`, even if an actual duration exists;
- completed tasks with `COMPLETED_TASK_NOT_ELIGIBLE`;
- started tasks with `STARTED_TASK_NOT_SUPPORTED` because remaining duration is undefined;
- duplicate task IDs in a problem through `validate_unique_task_ids`.

The returned task input marks prediction eligibility `MODEL_FEATURE_UNIT_UNVERIFIED`; known estimate units alone do not certify a trained legacy model.

## 3. Structured prediction provenance

`backend/app/domain/prediction_provenance.py` adds `PredictionStatus` and immutable `PredictionResult`. The result records task identity, candidate hour, value and score unit, source/status, model training state, history count and its availability state, model version and explicit version status, fallback state, typed duration provenance, validity, optimizer eligibility, and an optional reason. Its validation rejects contradictory status/value combinations. `model_version` stays `None` with `model_version_status=MODEL_VERSION_NOT_AVAILABLE`.

`PredictionEngine.predict_task_hour_with_provenance` is additive; existing scalar and batch APIs are unchanged. It requires an explicit `DurationValue` and a valid integer RL action hour 6–22. It delegates to the existing behavior engine and does not change the cold-start formula or model training implementation.

- Cold start is labeled `COLD_START_HEURISTIC`, `model_trained=false`, `fallback_used=true`; empty current behavior data yields a real row count of zero. It is not personalized and reports `optimizer_eligibility=COLD_START_NOT_ELIGIBLE`.
- Trained state comes from `ProductivityModel.is_trained`. `history_count` uses `training_data_shape[0]` only when available; otherwise it is `None` / `UNAVAILABLE`. This count does not prove target quality or unit consistency.
- Trained legacy-model output is labeled `TRAINED_MODEL` but carries `optimizer_eligibility=MODEL_FEATURE_UNIT_UNVERIFIED`.
- Missing engine/model state yields `UNAVAILABLE`; malformed task type/duration or invalid score yields `INVALID_INPUT` without a score.

No model version is invented. Persisted artifacts expose training-data shape but no semantic model version. A trained flag only says an artifact/model is trained or loaded; it does not certify feature units.

## 4. Legacy model mismatch and matrix state

`ProductivityModel.train` documents duration as minutes; `predict` documents hours. Both paths pass raw numeric duration features without conversion. Existing model artifacts and `BehaviorData.duration` have no unit provenance sufficient to resolve that mismatch. The F9.1C method passes explicit normalized hours but marks trained results optimizer-ineligible; it does not claim the old artifact was trained in hours.

No training, artifact rewrite, database migration, schedule integration, or task x hour matrix was performed. The matrix remains **NOT READY** until feature units are resolved with a versioned training/data contract, provenance is trustworthy, and a real eligible model/data path can be checked for non-triviality.

## 5. Compatibility and protection

- `Task.estimated_duration` and `Task.actual_duration` names and current endpoints are unchanged.
- `PredictionEngine.predict_productivity` and `predict_batch` are unchanged.
- `RLScheduler`, `OptimizationEngine`, `DecisionPipeline`, frontend, ORM schema, and stored task/behavior rows are unchanged by F9.1C.
- No QUBO, Ising, QAOA, quantum execution, optimizer, hybrid comparison, weights, or synthetic history was added.

## 6. Tests and validation

Focused coverage is in `backend/tests/test_f9_1c_data_contract.py`. It checks conversion/provenance, invalid and unknown units, legacy-value preservation, no actual-duration substitution, task/lifecycle eligibility, current lifecycle minutes, cold-start and trained-model provenance, unavailable version/history count, invalid provenance, and public Task API field compatibility. These use isolated in-memory data and model stubs; they do not write production records or create user training history.

## 7. Deferred requirements

1. Establish a versioned unit contract for new Task API writes without changing legacy fields.
2. Resolve or reject historical estimate/model feature units using evidence; never mass-divide legacy values.
3. Retrain/validate a new model only after a trustworthy dataset and feature schema exist.
4. Add source/version metadata to persisted model artifacts when a concrete model-version policy is approved.
5. Build a provenance-complete matrix only after the above and the production non-triviality gate pass.
