# F9.1B — Data Semantics and Optimization Input Contract

**Status: PARTIAL — audit and future contract documented; no normalization code implemented.**

This document separates the intended architecture in Synopsis Major(8) from the repository's current behavior. Synopsis Major describes historical task/behavior data feeding ML predictions and planning, followed by classical optimization and later quantum suitability/QUBO/Ising/QAOA paths, hybrid comparison, executive recommendation, and feedback. This phase defines the input semantics that a future optimizer would need; it does not implement those later layers.

## 1. Finding

There is no globally authoritative unit for the persisted `Task.estimated_duration` field. The current task form says minutes and the F.3 dataset adapter maps the ORM value to `estimated_duration_minutes`; scheduling arithmetic treats the same untagged value as hours. `Task.actual_duration` is minutes when written through the current lifecycle service, but old rows and other writers have no unit/version marker. Behavior-model training and inference pass raw duration values without a conversion, and the model's own train and predict documentation disagrees.

Consequently, optimizer-facing durations cannot safely be normalized from existing ORM values alone. A numeric conversion such as dividing by 60 would create a plausible unit conversion but cannot prove what an individual historical value meant. Do not apply such a conversion to persisted rows, cached `BehaviorData`, or model artifacts in this phase.

### Answer: estimated duration

`Task.estimated_duration` has no established system-wide unit. The current UI and F.3 adapter provide minutes evidence for specific paths; the scheduler, `PlanTask` bounds/consumers, workload displays, and prediction assumptions provide hours evidence in other paths. API/ORM storage has only an untagged float, with no universal maximum (API and lifecycle accept any positive finite value; some unrelated domain code has its own 24-hour bound). Therefore `estimated_duration_hours` is appropriate as a **future normalized internal field name**, not as a retroactive claim about current storage. A global allowed maximum is not established and must be decided before code validation can impose one.

### Answer: actual duration

For `TaskLifecycleService.complete_task` writes, the stored value is elapsed minutes derived from timestamps. The optional API `actual_duration` is also interpreted and validated as minutes on this path. The field's public/database name remains unitless. Other readers (notably `SchedulingEngine`, RL scheduling, `OptimizationEngine`, and `PredictionEngine`) can select `actual_duration` as though it were hours when an estimate is absent. These paths are unit-unsafe. Do not repair stored values by assumption.

## 3. Training labels and observed outcomes

The existing behavior-model pipeline and the separate F.3 duration dataset must not be conflated:

| Value | Classification | Evidence / meaning |
|---|---|---|
| Current lifecycle `actual_duration` | **OBSERVED / DERIVED FROM OBSERVED** | Elapsed timestamp difference in minutes; optionally supplied value must agree with timestamps. Legacy values without trusted provenance remain **UNKNOWN**. |
| ORM estimate copied into behavior history | **UNKNOWN unit** | The legacy behavior pipeline copies raw value; UI/F.3 path uses minutes, scheduler path assumes hours. Unit is not retained in the resulting behavior row. |
| Legacy productivity model feature `duration` | **DERIVED FROM OBSERVED or UNKNOWN** | Preferentially actual duration; estimate fallback. It is raw and may mix units/sources. |
| Legacy `completion_time` | **DERIVED FROM OBSERVED / estimate** | Ratio of raw duration to raw estimate, clipped `[0.25,3.0]`; only dimensionless if units match. The current code does not enforce that premise. |
| Legacy `productivity_score` target | **HEURISTIC** | Deterministic combination of focus score, energy curve, and inverse completion ratio. It is not an observed productivity outcome or ground truth. |
| Legacy `focus_score`, `energy_level` | **HEURISTIC** | Formula-derived from priority, duration ratio, and hour-of-day. |
| F.3 `duration_ratio` target | **DERIVED FROM OBSERVED** | Actual minutes divided by prediction-time estimated minutes, with timestamp-derived actual when needed. It is a separate target contract; it is not the legacy productivity score. |
| Cold-start profile / score | **SYNTHETIC HEURISTIC** | Static defaults with `tasks_analyzed=0`; fallback prediction depends on hour only. Not personalized history. |

`BehaviorIntelligenceEngine.collect_behavior_data` selects completed rows with start/end times but does not filter `outcome_valid` or require a lifecycle-state value. Its legacy feature generator uses deterministic formulas; training on those rows does not turn the labels into ground truth. Existing model artifacts do not carry an exposed semantic version/unit contract sufficient to establish their training feature units.

## 4. Future normalized duration and task input contracts

These are **design requirements**, not current production classes:

```text
DurationValue:
  original_value: finite positive number
  original_unit: "minutes" | "hours" | "unknown"
  normalized_hours: finite positive number | unavailable
  source: explicit field/source identifier
  conversion_applied: explicit conversion description | "none" | "not_permitted"
  unit_provenance: explicit, validated, or unknown
```

An optimizer-facing task must only receive `estimated_duration_hours` when a trusted source explicitly establishes the original unit and conversion. Unknown-unit values must be rejected or marked ineligible; no `unknown -> hours` default is allowed. The source value and unit provenance must remain attached. Do not automatically use actual duration as a substitute estimate: actuals are post-outcome data and can leak future information into prediction-time input.

```text
OptimizationTaskInput:
  task_id: stable existing Task.id
  task_type: existing non-empty task type
  priority: existing integer 1..5
  duration: DurationValue (estimate eligible for scheduling; actual is outcome-only)
  lifecycle_state: existing created/started/completed value, or explicitly unavailable
  completed: existing boolean
  outcome_valid: existing nullable boolean
  prediction_eligibility: derived validation result, not a new persisted fact
  prediction_source: provenance enum, not currently exposed by prediction output
  training_state: provenance enum plus known sample/history count where available
```

Only tasks eligible for future planning may enter a problem. The initial contract should reject completed tasks. `started` tasks require a separately defined remaining-duration/pause contract and are not automatically eligible. Missing lifecycle fields cannot be silently defaulted to a fabricated state.

No deadline, goal, resource, or remaining-duration field is added by this contract; those values must not be invented.

## 5. Candidate-hour and prediction provenance contracts

`RLScheduler.available_actions` is currently `list(range(6, 23))`, i.e. integer start hours 6 through 22 inclusive. This is an **action-space implementation detail**, not documented proof of user working hours. Other scheduling code has separate window defaults, so the RL range must not be generalized as a global calendar policy. For the bounded F9 matching experiment only, a candidate hour can be represented as an integer in `[6,22]` with source `RLScheduler.available_actions`; the exact proposed set must be preserved. Duplicate RL fallback hours invalidate an at-most-one matching problem.

Every future prediction entry must carry at least:

```text
task_id, candidate_start_hour, prediction_value,
prediction_source, model_trained, history_count,
model_version (nullable/unavailable today), fallback_used,
duration_feature (with unit/provenance), score_unit="productivity_points",
validity/status
```

Allowed source/status distinctions: `TRAINED_MODEL`, `COLD_START_HEURISTIC`, `UNAVAILABLE`, `INVALID_INPUT`. Current `BehaviorIntelligenceEngine.predict_task_productivity` returns a scalar; `PredictionEngine` adds a score but neither exposes the full requested provenance contract. `ProductivityModel` has an in-memory `is_trained` flag and `training_data_shape`, while the persisted artifact has no model version surfaced through prediction; history count and `fallback_used` are not attached to the value. **Prediction provenance: FAIL (not contract-complete).**

## 6. Task x hour matrix and eligibility

Matrix state: **MATRIX_NOT_READY**. The predictor can be called for a supplied hour/task type/duration, but that alone is not sufficient: duration feature units conflict, label semantics are heuristic, current canonical planning evaluates one resolved hour per task, and outputs omit required provenance. Do not build or fabricate `score[t,h]` in this phase.

For future entries, `score[t,h]` must be a structured prediction record, not a bare scalar. Matrix construction must enumerate only real eligible tasks and unique valid candidate hours, preserve deterministic task/hour ordering, and refuse to extrapolate when prediction provenance is unavailable or invalid.

Define the non-triviality gate on evaluator-valid assignments. For at least one pair of distinct tasks A/B and hours h1/h2, require:

```text
abs((p[A,h1] + p[B,h2]) - (p[A,h2] + p[B,h1])) > epsilon
```

`epsilon` must be a declared score-unit numerical tolerance (for example, `1e-9` productivity points for binary64 arithmetic), fixed and recorded for the contract version. This is only an eligibility test. No real production matrix/model artifact was inspected or demonstrated to pass; therefore production eligibility is **UNKNOWN**, and the optimization path is **NOT_ELIGIBLE until verified**. The deterministic cold-start heuristic cannot pass because it is hour-only and task-independent.

## 7. Deterministic `OptimizationProblem` validation requirements

Reject before a solver is called unless all of these hold:

1. Task set is non-empty; task IDs are stable, non-empty, and unique.
2. Each task has supported non-empty type, valid priority, and explicit lifecycle/completed/outcome fields; completed or unsupported lifecycle states are excluded.
3. Required estimated durations are finite, positive, unit-known, source-identified, and normalized to hours with conversion provenance. No arbitrary universal maximum is asserted until the product chooses one.
4. Candidate hour set is non-empty, unique, integer-only, and within the selected domain (for the bounded RL problem, 6..22); preserve its source and exact order/canonical ordering.
5. Task/hour cardinality satisfies the selected matching contract; the F9.1A perfect matching proposal requires `|T|=|H|`, at least two tasks for a non-triviality test, and no more than 17 distinct RL actions.
6. Every matrix cell exists exactly once for the task/hour key, has finite score in the existing `[0,100]` prediction range, and carries valid source/training/history/fallback/duration provenance.
7. A trained prediction must identify model training state and available sample count; cold-start predictions are never labeled personalized or eligible for task-hour optimization.
8. No matrix is accepted if any required cell is unavailable/invalid or if the assignment objective fails the declared non-triviality tolerance.
9. No unknown unit, untrusted fallback, duplicate identity, missing field, non-finite value, or silently defaulted lifecycle state may enter a problem.

These validation rules are documented only; no validator or optimizer was implemented.

## 9. Remaining blockers

- No authoritative global unit for existing `Task.estimated_duration`; the UI and F.3 interpretation (minutes) conflict with hour-based runtime arithmetic.
- ORM `Task.actual_duration` has no stored unit/source version; current lifecycle writes minutes, but legacy and external writer provenance is not established.
- `BehaviorData.duration` has no unit or source metadata and can mix actual and estimated raw values.
- Legacy `ProductivityModel` training receives unnormalized values; train/predict docs say different units; no model semantic version/training provenance is surfaced.
- The legacy productivity target is heuristic-derived, not measured productivity; the separate F.3 ratio target is not shown feeding the legacy predictor.
- Prediction output omits model version, training sample/history count, source, and fallback status; cold-start path returns only a scalar hour heuristic.
- No full task x hour prediction matrix or verified production non-triviality evidence exists.
- Universal maximum task duration and policy interpretation of 6..22 as working hours have not been established.
