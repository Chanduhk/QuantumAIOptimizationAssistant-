# F9.0 Optimization Problem Specification

**Status: design prepared; implementation not authorized in this phase.** This document records current repository semantics and a conditional, source-grounded scheduling formulation for review before F9. It does not claim QUBO construction or quantum execution has been implemented.

## 1. Current scheduler limitation

The canonical `DecisionPipeline.optimize_schedule` runs `RLScheduler.optimize_schedule` and then passes those results through `OptimizationEngine.optimize_schedule`. The RL stage chooses an integer start hour from actions 6–22, avoids reusing a start hour while an unused action remains, and records a heuristic reward. The later optimization stage ranks the distinct input hours by `hourly_productivity`, ranks tasks by predicted productivity, and pairs them in order. Its optimized score is the sum of hour productivity values. The task-to-hour pairing therefore does not affect that score. The RL reward is retained as `schedule_score` for a baseline comparison; it is not the later optimizer's objective.

Sources: `backend/app/pipeline/decision_pipeline.py::optimize_schedule`; `backend/app/ai_rl/rl_scheduler.py::optimize_schedule`, `_calculate_reward`, `_pick_available_hour`; `backend/app/engines/optimization_engine.py::optimize_schedule`.

## 3. Decision variables and scheduling semantics

For a problem with required task set `T` and supported candidate integer start-hour set `H`, define:

`x[t,h] ∈ {0,1}` iff task `t` starts at hour `h`.

`H` is currently sourced from the RL action range 6 through 22 inclusive. The scheduler permits durations represented as positive floats and computes `end = start + duration`; it does not use duration to reserve multiple slots. Fractional-hour durations therefore exist, but fractional start slots are not in the RL action set.

Proposed validity conditions are deliberately limited to implemented behavior:

- Every supplied task is assigned to exactly one start hour.
- Each start hour is used by at most one task, for instances with no more than 17 tasks. The current `_pick_available_hour` repeats its preferred hour if all 17 actions have been used, so larger inputs do not satisfy uniqueness and require a separate policy decision.
- Start hours are within the existing action set 6–22.
- Duration is positive and finite, using the existing estimated/actual/default resolution. Duration determines reported end time only.

The model does **not** assert non-overlapping time intervals, working-day capacity, task splitting, deadline feasibility, or dependency ordering: those are not enforced by the canonical scheduler. Dependencies are analyzed elsewhere, but no time precedence is applied in this scheduling path. Existing task records have no deadline column.

## 4. Hard constraints

| Name | Mathematical form | Code evidence | Why hard in this limited contract | Validation |
|---|---|---|---|---|
| Exactly one slot per input task | `Σ(h∈H) x[t,h] = 1` for each `t` | `RLScheduler.optimize_schedule` emits one result for each iterated task | Missing or duplicate assignment is not a complete schedule | Count assignments per task; require count = 1 |
| Valid start hour | `x[t,h]=0` for `h∉{6,…,22}` | `RLScheduler.available_actions` and `choose_action` | Out-of-domain action is not supported | Validate integer hour in action set |
| Unique start hour (bounded scope) | `Σ(t∈T) x[t,h] ≤ 1` for each `h` | `used_hours` plus `_pick_available_hour`; only guaranteed while an unused action remains | It is the current canonical RL start-hour collision rule, but only for `|T|≤17` | Count tasks per start hour; reject more than one |
| Positive duration | `duration[t] > 0` and finite | `SchedulingEngine._resolve_duration`, `OptimizationEngine._resolve_duration` | Invalid task input cannot form a valid schedule | Reuse existing duration validation |

These constraints do **not** establish non-overlap. Enforcing non-overlap for fractional durations would require a separately specified interval/resource model; current code has no such rule.

## 5. Proposed objective: conditional and source-grounded

The only existing project signal that can create a task-by-hour interaction without inventing a weight is the existing predictor's output for a particular task type, duration, and hour:

`p[t,h] = clamp(BehaviorIntelligenceEngine.predict_task_productivity(hour=h, task_type=t.task_type, duration=t.duration), 0, 100)`

Proposed objective:

`maximize Σ(t∈T) Σ(h∈H) p[t,h] · x[t,h]`

- Term: predicted productivity for a task at a candidate hour.
- Source: `backend/app/services/behavior_engine.py::predict_task_productivity`; the production model receives hour, task type, and duration. `backend/app/engines/prediction_engine.py` already validates/clamps predictor output to 0–100.
- Unit: model productivity score, 0–100 per assigned task; total is the sum of those scores. For fixed `|T|`, maximizing the sum is equivalent to maximizing its mean.
- Sign: maximize.
- Normalization: retain the predictor's existing [0,100] scale; add no new weights or fabricated factors.
- Why assignment can matter: if the trained model produces task-specific hour response, swapping two different tasks across two different slots changes the sum. This must be confirmed from real model behavior before F9 calls it a personalized objective.

**Cold-start limitation:** when no behavior rows exist and the model is untrained, `predict_task_productivity` returns `75 + 10*(1-|h-10|/12)`. This value depends on hour only, not task type or duration. Then assignment permutations across a fixed slot set remain equal. The fallback must be marked non-personalized; it cannot satisfy a claim that task-to-slot pairing is non-trivial. Since `tasks_analyzed == 0` is explicit, F9 should either route to classical-only for this formulation or establish a separately approved, non-fabricated signal. No synthetic observations should be created.

## 6. Non-triviality check

For tasks A/B and candidate slots h1/h2, the swap difference is:

`Δ = p[A,h1] + p[B,h2] - p[A,h2] - p[B,h1]`.

The formulation is non-trivial for task assignment only when `Δ != 0`, which is equivalent to task-specific hour response not being perfectly separable. This is an algebraic check, not a benchmark claim.

Illustrative deterministic fixture (not user data or a claim about observed project users): let the existing predictor return `p[A,10]=90`, `p[A,14]=60`, `p[B,10]=50`, `p[B,14]=80`. Schedule A→10/B→14 scores 170; A→14/B→10 scores 110. These are valid values on the predictor's existing 0–100 contract and demonstrate the required test shape. A real test must inject a deterministic predictor fixture in isolation; production must use the actual predictor and its provenance. The cold-start formula itself does not exhibit this distinction.

## 7. Shared conceptual contract and evaluator

No new model is implemented in F9.0. The F9 implementation should define/reuse typed contracts with fields equivalent to:

- `OptimizationProblem`: `problem_id`, immutable task inputs, ordered time slots, decision-variable index, objective definition/provenance, hard constraints, metadata (including observed-history count/model-trained state).
- `OptimizationCandidate`: assignments `(task_id, start_hour)`, solver, runtime, and evaluator-populated feasibility, violations, objective value, and metrics.
- `OptimizationComparison`: both evaluated candidates, common metrics, selected candidate, and evidence-based selection reason.

`evaluate(candidate, problem)` is the sole authority for candidate validity and score. It must independently validate assignment counts, slot domain, start-hour uniqueness, and duration inputs; then recompute the objective from `p[t,h]`. A solver-supplied score is advisory only and must not be used for comparison. Both classical and QAOA outputs pass through this evaluator.

## 8. Classical solver mapping and gap

`RLScheduler` is the current first assignment mechanism but is not an exact/global optimizer for the proposed objective: it uses an epsilon-greedy Q-table policy, chooses one hour per task sequentially, and its reward uses a task-constant predicted-productivity value computed before slot assignment. It can produce a feasible incumbent for up to 17 tasks, but it does not evaluate `p[t,h]` for every candidate pair.

Then `OptimizationEngine` remaps tasks over the distinct RL-selected hours and scores only hourly productivity. Thus the final canonical schedule does not preserve a candidate's score under the proposed objective.

**REQUIRED CLASSICAL SOLVER GAP:** add a deterministic classical search/solver over the exact same `x[t,h]` domain and common evaluator; retain it as the baseline candidate in the canonical pipeline. The existing RL output may be supplied as an additional incumbent only after the common evaluator recomputes its value. Do not represent the current final schedule as optimized for the proposed objective until this gap is closed.

## 9. QUBO representability

For the proposed bounded binary assignment model, with `N=|T|·|H|` variables:

- The objective is linear: maximize `Σ p[t,h]x[t,h]` (or minimize its negation).
- Exactly-one constraints can be penalty-encoded as `A(1-Σ_h x[t,h])²`.
- At-most-one start-hour constraints can be penalty-encoded as `B Σ_{t<u} x[t,h]x[u,h]`.
- Both penalties must be derived from a proven bound on the complete objective range for the supplied problem and chosen so any infeasible assignment cannot beat a feasible one. Do not select fixed arbitrary weights.
- Coefficients are finite if validated predictions are finite and bounded. Variable ordering must be deterministic (stable task IDs then ascending slots).
- Non-overlap, deadline and dependency precedence are **not currently representable from supported canonical inputs** because those semantics are not present as enforced scheduling constraints. They are excluded, not approximated.

Mathematical QUBO representability: **PARTIAL/CONDITIONAL**. The QUBO is valid for the limited assignment contract if data-backed pair scores and justified penalties are available. It is not yet a justified production QUBO because the canonical solver and score pipeline do not implement that contract, and the cold-start model fails the task-hour interaction check.

## 10. Suitability criteria for future F9

Before considering simulator limits, require: (1) supported optimization contract; (2) finite, deterministic task-hour scores from an explicitly identified predictor state; (3) valid binary variables and mathematically justified penalties; (4) all candidate constraints supported and independently checkable; (5) a common-evaluator classical candidate available. Then apply existing `QuantumSuitabilityAnalyzer` limits (`allow_quantum`, variable count, QAOA max qubits/shots, estimated state count). Suitability is resource/formulation feasibility, never a claim of advantage. With 17 slots, `N=17|T|`; current default maximum 8 variables implies most nontrivial assignment instances will route to classical fallback.

## 11. Current factor gaps

- No task deadline field in `backend/app/models/task.py`; optional deadline urgency exists in `DecisionEngine`, but not as a persisted hard scheduling window.
- No canonical working-hours/capacity resource model; RL's 6–22 values are actions, not occupied one-hour bins.
- Fractional duration is accepted, but interval overlap is not enforced.
- Dependencies are detected and can mark tasks blocked, but canonical time assignment does not impose predecessor completion before successor start.
- Stress/overload, future risk, compression, and strategic scores are computed in separate engines with different scales and horizons; none is a calibrated task-hour objective component.
- Behavior cold-start defaults are deterministic priors, not learned user evidence.
- Canonical classical output is not evaluated by a shared assignment objective.

## 12. Test design (not implemented)

1. Reject duplicate/missing task IDs and invalid binary assignments.
2. Validate exact-one, allowed-hour, unique-start-hour, and bounded task-count behavior.
3. Recompute score and feasibility independently of solver-provided fields.
4. Verify deterministic task/hour score matrix and objective evaluation.
5. Use isolated deterministic predictor outputs to prove a task-hour swap changes the objective as shown above.
6. Verify cold-start predictor produces no task-specific swap advantage and does not claim personalization.
7. Evaluate a classical incumbent through the same evaluator.
8. Verify QUBO penalty validity by exhaustive enumeration for small fixtures.
9. Verify deterministic variable ordering and coefficients.
10. Verify all infeasible assignments lose to feasible candidates under derived penalty bounds.

## 13. What F9 must implement next

After approval of the objective and resolution of the classical solver gap, F9 can add the shared optimization contracts/evaluator, make the canonical classical planner solve and report this exact problem, form QUBO from the same validated score matrix, apply existing QUBO→Ising→QAOA modules only when suitable, validate both candidates through the shared evaluator, and pass comparison evidence to the Executive Cognitive Brain. It must preserve classical fallback and must not claim hardware use or quantum advantage.
