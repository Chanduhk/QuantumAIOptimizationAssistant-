`BehaviorIntelligenceEngine.extract_features` calculates productivity labels from priority, duration ratio, start hour, and a deterministic energy curve. The resulting model prediction is therefore trained on heuristic-derived labels, not direct observed productivity measurements. Real task history is required for that model path; cold start uses a fixed hour heuristic. Both limitations must travel with any later score.

## Current formal scheduling boundary

The narrowest supported binary representation is `x[t,h] ∈ {0,1}`, where `x[t,h]=1` means input task `t` receives integer **start hour** `h∈{6,…,22}`. The current RL scheduler emits one start hour per iterated task and avoids duplicate starts only while an unused action remains. Duration is a positive float and is used to compute an end timestamp, but is not discretized into occupied slots. Task splitting, non-overlap, deadlines, task omission, daily capacity, and dependency precedence are not enforced by this path.

Supported hard rules for a bounded reference problem would be exactly-one start hour per task, start-hour domain 6–22, and unique start hours only for at most 17 tasks. This describes current implementation behavior; it does not imply a safe real-world no-overlap schedule.

## Why no defensible multi-objective schedule objective exists yet

1. `OptimizationEngine` maximizes only the sum of selected hourly productivity scores. For fixed chosen hours it is invariant to task/hour permutation.
2. The RL reward is also separable: `r(t,h)=T(t)+H(h)` under `_calculate_reward`. Therefore `Σ_t r(t, assignment(t)) = Σ_t T(t) + Σ_h∈selected H(h)`, independent of which task receives which selected hour. Its epsilon-greedy Q-table policy is not a shared global objective.
3. `DecisionEngine` has a source-defined weighted score with real constants, but it ranks tasks; every task is currently assigned, so the total task score is constant across schedules.
4. The only plausible pair signal is a prediction evaluated at each task/hour. The canonical pipeline computes predictions at one hour per task; evaluating all pairs is a new use of the predictor. When trained it depends on real task history, and its labels are heuristic-derived. In cold start its formula is hour-only, so task swaps on a fixed slot set remain tied.
5. Other numeric signals are task-only, hour-only, whole-horizon, or executive summaries. No current verified signal set forms a source-aligned **multi-objective** task-slot objective with genuine assignment trade-offs.

A test fixture could prove that arbitrary different task-hour scores yield different assignments, but that would only prove the evaluator algebra; it would not prove those scores are generated by the current production path or sufficiently supported for a production objective. F9.1 therefore does not present synthetic scores as evidence or implement a solver around them.

## Multi-objective method audit

- **Weighted sum:** exists in `DecisionEngine` for task ranking and `MultiObjectiveOptimizationEngine` for simulation scenarios. Neither is a weighted task-slot schedule objective. Do not reuse them outside their current meanings.
- **Lexicographic:** no canonical lexicographic schedule policy found.
- **Constraint priority:** no canonical objective hierarchy for schedule candidates found.
- **Pareto:** the multi-objective scenario engine computes a weighted ranking; it does not compute a Pareto frontier. No schedule Pareto comparison exists.

No multi-objective schedule method is justified by current semantics.

## Shared contracts/evaluator/solver gate

A future shared contract should retain immutable task inputs, candidate start slots, objective definitions with provenance, constraint definitions, cold-start/training metadata, and deterministic variable ordering. Candidate records should carry assignments and solver/runtime metadata. An authoritative evaluator must independently compute feasibility, violations, and each objective value for every solver candidate. A comparison record should preserve all objective values and only select according to a previously approved comparison policy.

These are design requirements only. Implementing them now would require an approved objective/comparison policy that this repository does not supply. A classical exact/reference solver cannot be scientifically evaluated until that contract has a valid objective. Thus:

- Common evaluator: **NOT IMPLEMENTED**
- Classical reference solver: **NOT IMPLEMENTED; blocked on formal objective**
- Objective-difference proof from production-supported signals: **FAIL / not established**
- QUBO representability: **NOT READY for an approved production problem**

## Explicit next requirements

Before F9 can proceed, the project must supply or approve source-aligned decision semantics that cause a task-hour assignment to change candidate outcomes. Acceptable ways to close the gap include:

- operationalizing and provenance-tagging a trained per-task/per-hour predictor, defining behavior when history is absent, and approving whether its single score is sufficient or which additional objectives must be compared; or
- adding a real supported task-hour signal/constraint and its validated source data through a separately authorized architecture change.

If multiple objectives are required, define a comparison rule without arbitrary weights (for example, an expressly approved lexicographic order or constrained objective). Specify hard interval/capacity/dependency semantics only if the product intends and the application can enforce them. Then implement the classical reference solver and common evaluator against that same contract before QUBO.
